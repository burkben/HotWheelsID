# 15. A real external display ("TV mode") and an iPad-shaped layout

- **Status:** Accepted
- **Date:** 2026-07-25
- **Deciders:** HotWheelsID maintainers
- **Related:** [ADR-0005](0005-ui-toolkit.md), [ADR-0006](0006-state-management-and-persistence.md)

## Context

Two complaints from testing on an iPad, and they turn out to share a root cause.

**"There's no TV mode."** The roadmap has listed "TV/host mode" since Phase 5 was written, but
nothing shipped. Turning on AirPlay just mirrored the device — the TV showed the same phone-shaped
column the iPad was showing, letterboxed. A race night wants the opposite: the big screen shows the
lap clock and the standings for the room, while the person running the race keeps the controls in
their hands.

**"The iPad is a stretched phone."** Every screen centred a ~420pt column and `app.json` pinned
`orientation: portrait`, so an iPad in its natural landscape orientation was showing a portrait
phone UI with grey on both sides. The specific ask was the obvious one: the speedometer on one side,
the race results on the other.

The shared cause is that the app only ever modelled one shape of window. Fixing the TV without
fixing the layout would just put a portrait column on a 16:9 panel.

### What iOS actually requires for a non-mirrored display

Since iOS 16, `UIScreen.didConnectNotification` is deprecated and a *dedicated* external screen is
delivered as a **scene** with the `.windowExternalDisplayNonInteractive` role. A scene of that role
is only ever created if the app declares `UIApplicationSceneManifest` →
`UIApplicationSupportsMultipleScenes = true`. Without it, iOS has no way to give the app a second
window and falls back to mirroring — which is exactly what was observed.

Neither React Native 0.85's `RCTAppDelegate` nor Expo implements any `UIScene` handling; RN creates
`self.window` in `didFinishLaunchingWithOptions` and UIKit's compatibility path attaches it to the
first connected scene.

### Three ways to render on that scene

1. **Native re-implementation.** Write the TV UI in SwiftUI and push state across the bridge.
   Rejected: it duplicates every screen's logic in a second language and immediately drifts.
2. **A second React Native instance.** A whole new `RCTHost`, its own JS runtime. Rejected: double
   the memory, and the stores would be *separate copies* — the TV would need a full state-sync
   channel to show the same race.
3. **A second React *surface* on the existing host.** `RCTRootViewFactory.viewWithModuleName:`
   calls `createReactHostIfNeeded` then `reactHost.createSurfaceWithModuleName:`. Despite its name,
   Expo's `ExpoReactNativeFactory.recreateRootView(...)` forwards to exactly that and does **not**
   tear down the main root view.

## Decision

**The TV is a second React surface on the app's existing host**, mounted into a `UIWindow` on the
external-display scene.

Because both surfaces share one JavaScript runtime, and the Zustand stores are module singletons in
that runtime, the TV sees live state with **no bridging code at all** — a pass recorded on the phone
re-renders the TV in the same tick. This is the entire reason option 3 wins.

**The factory reference comes from Expo's `reactDelegateHandlers` hook.** A handler registered in
`expo-module.config.json` receives `createReactRootView(reactDelegate:...)` when the *main* root
view is built. `ExternalDisplayReactDelegateHandler` stashes the `ExpoReactDelegate` (which owns
`reactNativeFactory`) and returns `nil` to decline ownership. The alternative — reading
`reactNativeFactory` off the app delegate — depends on the shape of the prebuild-generated
`AppDelegate.swift`, and `/ios` is regenerated by CNG on every build. The handler hook is public
Expo API and survives regeneration.

**Layout is resolved from the window, not the device.** `resolveLayout(width, height)` is a pure
function with a single `TWO_PANE_MIN_WIDTH = 900` breakpoint. A `Platform.isPad` check would be
wrong in iPadOS Split View and Stage Manager, where the app gets an arbitrary-width window and a
half-width iPad should read like a phone. Keeping it pure means the breakpoints are unit-tested
under Node, which matters because the vitest setup stubs React Native and cannot mount hooks.

**iPad rotates freely; iPhone stays portrait.** Expo's `orientation` field only writes the
non-suffixed `UISupportedInterfaceOrientations`, so a hand-written
`UISupportedInterfaceOrientations~ipad` in `ios.infoPlist` coexists with it cleanly.

## Consequences

**Good.**

- The TV genuinely runs its own UI. The device keeps its controls; the big screen shows the race.
- Zero state-sync code, and no risk of the two screens disagreeing.
- `TvStage` is one component used by both the external surface and the in-app `/tv` screen, so the
  feature degrades to plain mirroring on Android, on the web, and in Expo Go, and can be previewed
  without a TV in the room.
- Screens branch on `layout.isSplit`, so Split View, a rotated iPad and a phone all fall out of the
  same rule set rather than three code paths.

**Costs and risks.**

- `UIApplicationSupportsMultipleScenes` also unlocks **iPad multi-window**. React Native only
  attaches its root view to the app delegate's window, so a second *application* window would
  render blank. `ExternalDisplayController` therefore mounts the TV stage into any extra
  application-role scene as well — a blank window would be a bug, a second race display is a
  feature.
- A TV attached *before* launch connects its scene before React Native is ready. Those scenes are
  parked in `pendingScenes` and replayed once the delegate is adopted.
- `TvStage` must never import `expo-router`: the external surface has no navigation context.
- The iOS Simulator cannot simulate an external display, so this path is only verifiable on real
  hardware with AirPlay or a cable.
- `TvStage` measures itself with `onLayout` rather than `useWindowDimensions()`, because RN's
  `Dimensions` reports the *device* screen and would size the TV to the iPad.

## Alternatives considered

- **`expo-screen-orientation` for the rotation half.** Rejected: it changes orientation at runtime
  per-screen, when what was wanted is a static per-idiom capability. The Info.plist key says exactly
  that and costs no dependency.
- **AirPlay route APIs to name the display.** `UIScreen` exposes no human-readable name; getting one
  means `AVAudioSession` route inspection, which is a lot of machinery for a subtitle. The TV screen
  falls back to "the connected display".
